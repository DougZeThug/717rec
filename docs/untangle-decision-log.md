## Unrated division result (career bonus), built 2026-11-16 (migration file `20261117120000`)

An unknown division is **unrated** in the career bonus: it adds 0 instead of counting as 0.85. TypeScript and SQL give the same number, except for a division name with a leading tab or a non-breaking space: TypeScript rates it and SQL leaves it unrated (see the migration header and fixture 13). **The SQL was applied to the live database by Doug on 2026-11-16, before PR #1744 was merged** (`docs/OPERATIONS.md` section 6f). The fingerprint (count and md5 of `calculate_career_power_score` over all teams) was **identical before and after**: count 51, md5 `c4d29aa83f550d893309275afc806e5f` (Doug's screenshots; the SQL Editor reported "Success. No rows returned"). The resolver check gave 1.00 for `Competitive` and NULL for `zzz`. The optional `has_function_privilege` check was not reported back. No number changes today (live read 2026-11-13: every division has a weight, every past division name matches).

- **The rule (the same in both places).**
  - Unrated = a blank name, a name that matches no division, or a matched division with a NULL weight. A weight of 0 is a real 0.
  - A matched division with a NULL weight stops the lookup. It does not fall through to a synthetic label or a base tier word.
  - Title and runner-up: an unrated one adds 0 (the champion count still shows).
  - Playoff win-rate weight: the average over rated seasons only. With none rated it uses the team's current weight. If that is unrated too, the win-rate bonus is 0. The win rate still counts every playoff match. **This fallback is a developer choice (the simplest rule; the bonus is worth about 2 points or less). Doug can overrule it.**
  - Bonus cap: 15 x (the highest rated weight)^2. With none rated it uses the team weight. If that is unrated too, the whole bonus is 0.
  - The team's own weight has no default: `number | null`, and a stored 0 stays 0.
  - Not changed: the competitive-playoff count (an unknown bracket is not counted, in both places), Hidden division names.

## Browser finding (library crash), found by QA 2026-11-14

- **What happens (VERIFIED by QA in a real browser and in a production build):** `edmonds-blossom` 1.0.0 (`app/blossom.js`) assigns three variables it never declares: `b` and `path` in `addBlossom`, `v` in `expandBlossom`. ### The acceptance gate: first result, cause, fix, final result

**First result (commit `a4bc0ff`, VERIFIED by running the seeded grid).** The plan said: "ON makes no more rule-bending pairs than OFF" (a rule bend is a Competitive team against a Recreational team, or a repeated pair unless both teams are Recreational). I built a seeded grid: tier mixes 1/2/1, 2/2/2 and 3/1/2 (Competitive / Intermediate / Recreational, the pattern repeated to the block size), blocks of 6, 8 and 10 teams, 40 seeded blocks each, random ratings. ON bent more rules than OFF in 4 of 9 cases in the plain library (for example 1/2/1 at 6 teams: 23 bends OFF, 25 ON; ON worse in 11 blocks) and in 7 of 9 cases in the all-throw browser mode. The grid counted only bends. It did not check that Apply can place a list into the two time slots, and it stopped at 10 teams. QA-B showed both gaps matter.

**Cause (VERIFIED by QA-A, QA-B and one experiment of mine; it is a twist on my first guess).** Take a block of 6 with 2 Competitive, 3 Intermediate and 1 Recreational team. A smaller round 2 (T1-T3 and T2-T5, 15 points) and the full round 2 (T1-T3, T2-T4 and T5-T6, also 15 points) tie in OFF. In ON every pair loses a little, so the round with fewer pairs loses less and wins. Both OFF and ON pick the short round. Then they split: in OFF the first run fails and the existing retry (full rounds) makes a clean list. In ON the two leftover teams are Competitive and the only open partner is the Recreational team. The relaxed repair step accepts that 0-score pair, nothing throws, so the retry does not run. A constant +0.5 on every score (my scratch experiment, not committed) also removed these bends, which fits the same cause.

**The fix (F1, commit `a643717`).** With ON, the first run asks each round to pair as many teams as it can (the library's `maxCardinality` switch, which the retry already uses). A smaller round can no longer win. See the commit list above for the 3 changed lines and the rollback.
