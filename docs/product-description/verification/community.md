# Verification: community

How to run this file: the message board needs a **signed-in player** for almost
everything and a **second browser** signed in as a *different* account for the
live items — a second tab shares the session and will mask what two real users
would see. Have an **admin** to hand for the Announcement category and for the
signed-out comparisons, and a **private window** for every `visitor` item. The
help page needs nothing. **The contact form is the pilot for this directory and
two of its claims are already answered** — see the Result column below, and read
the warning above the `contact-the-league.md` table before running anything
there. Every message posted and every reaction added during a pass is a **real
write to the real league's board**, visible to everyone: post obvious test text,
delete it afterwards, and do not react to other people's messages. Device values:
`visitor`, `player`, `admin`, `browser`, `phone`, `offline`, `slow`,
`second browser`.

Not checkable by hand:

- How many open channels the board really holds with a full list on screen — the
  document says one for messages plus one per visible message — and whether that
  is a problem in practice. Needs instrumentation, not a look at the page. See
  [Open questions](../message-board/read-the-board.md#open-questions-and-verification).
- Whether the board pages by time rather than by position, and whether two
  messages stored in the same instant can straddle the boundary and one be
  skipped. Producing that collision needs the database.
- Whether the glossary or the database is right about a visitor reading the board.
  BOARD-06 gathers the evidence; which document to correct is a decision for the
  consistency pass.
- Whether the list's live region is announced by a screen reader when messages
  arrive. Needs a real screen reader; see
  [`cross-cutting/accessibility.md`](../cross-cutting/accessibility.md).

Not checkable by hand:

The success path cannot be exercised without a real message reaching a real
person. Each of these is **not checkable without sending a real message to the
league**, and stays `blocked` unless the league agrees in advance to receive and
ignore test messages:

- The success panel with a tick, "Message Sent!" and the "within 24-48 hours"
  promise, the "Message sent successfully!" toast that duplicates it, and whether
  the two appear together or one replaces the other. See
  [Submit](../help/contact-the-league.md#submit).
- "Send Another Message" returning to a blank form rather than the previous one.
- That the success panel is not a route, and a reload after success returns to an
  empty form with no evidence the message was sent.
- The server's own rules: a name over 100 characters, a message over 5000, an
  address over 255, more than five links, and five messages in ten minutes. All
  four produce the same generic toast, and confirming any of them means sending.
- That the honeypot discards silently while still showing the success panel —
  CONTACT-22 checks only whether a filler writes into the field.
- That two tabs, or a retry after a failure, can deliver the same message twice.

Also not checkable by hand:

- What the email looks like when it arrives and whether the reply-to works. That
  is a check of an inbox, not of this app, and belongs with whoever reads
  `admin@717rec.com`.
- Whether a screen reader announces the switch to the success panel. Needs a real
  screen reader and a real send.
- Whether "within 24-48 hours" is met. The document records it as a statement of
  intent by the league, not something the product enforces or measures.
- Whether the analytics event carrying the chosen subject is recorded, since it
  fires only on the published build and only on a successful submit.
